# 微服务与中间件

对应简历：Spring Cloud / Dubbo / Apollo / Eureka、RocketMQ / Kafka、Redis、Elasticsearch、Kubernetes、可观测性。资深面很少问「Kafka 是什么」，而是问你**在交易和对账里怎么用、出过什么问题**。

## Q1. 为什么交易链路用 RocketMQ，对账用 Kafka？可以反过来吗？

**怎么答**：

- 简历里成交、充提、强平走 RocketMQ；对账上游走 Kafka。合理叙事：
  - 交易侧要事务消息 / 延迟 / 业务积压隔离，和阿里系微服务常见组合。
  - 对账侧要长时间留存、回放、多消费组（计算、审计、数仓）。
- 反过来也能做，但要改运维和消息语义。重点是**你知道选型理由，不是背品牌**。

展开消费语义见现有 [KFK 笔记](/docs/R06-消息队列/0600-KFK笔记/060000)、[RMQ 笔记](/docs/R06-消息队列/0601-RMQ笔记/060100)。

## Q2. Dubbo + ZooKeeper 挂了注册中心，正在跑的交易会怎样？

**怎么答**：

- 已建立的连接通常还能调；新实例、扩缩容、恢复寻址会受影响。
- 要讲本地缓存、降级、不要把 ZK 当运行时数据总线。
- 对比 Eureka：AP 倾向，更强调自我保护；ZK 更偏 CP。简历两套都写过（交易平台 ZK，对账 Eureka），主动对比加分。

相关：[注册中心](/docs/R12-分布式/1201-注册中心/120100)。

## Q3. Apollo 动态配置在交易场景里哪些能热更，哪些绝对不能？

**怎么答**：

- 能热更：告警阈值、开关、限流、非核心文案、对账规则。
- 谨慎：手续费、风控阈值、撮合开关——要灰度、审计、可回滚。
- 不能：随便热更「账务精度、主键策略」。
- 配置变更本身要可观测：谁改了、生效到哪些实例。

## Q4. Redis 在你简历里出现了太多次，分别扮演什么角色？

**怎么答**，按项目拆，避免「缓存」一个词打天下：

| 项目 | Redis 角色 |
|------|------|
| 交易平台 | 盘口 / 持仓热数据 |
| 对账 | 规则缓存、最近差异 |
| 绩效 | 抗积压、分布式锁（Redisson） |
| 客服 | 会话与限流辅助 |
| 策略 / EVM | 去重、任务状态机 |
| ChatCMS | 缓存与消息辅助 |

追问到锁，走 [分布式锁](/docs/R04-Redis笔记/0403)；追问缓存与 DB 不一致，走 [缓存一致性](/docs/R04-Redis笔记/0406)。

## Q5. Elasticsearch 适合存什么，不适合存什么？

**怎么答**：

- 适合：对账异常明细检索、OTC / 币币经营统计查询、ChatCMS 全文检索。
- 不适合：资金余额 source of truth、撮合订单簿。
- 写入：近实时，不是事务库；对账结果先落 MySQL 再同步 ES。
- 面试官听的是：你没有把 ES 当账本。

## Q6. 网关在数据平台和交易平台里各做什么？

**怎么答**：

- 数据平台：登录、鉴权、路由到计算 / 下载中心，见 [网关鉴权](/docs/R12-分布式/1200-服务网关/120000)。
- 交易平台：限流、鉴权、把行情和交易流量分开，避免后台导出把下单打挂。
- 限流算法见 [服务限流](/docs/R09-编程思考/0901-服务限流)。资深表达：限流要按 **UID / IP / 接口** 分层，交易接口和下载接口配额不能共用。

## Q7. Kubernetes 弹性部署，撮合和委托服务都能随便扩吗？

**怎么答**：

- 无状态（网关、只读行情）：可扩。
- 有状态（某交易对撮合引擎、账户分区账本）：不能盲目 replicas+1，要按分片扩。
- 简历写「部分委托服务通过 Kubernetes 弹性部署」，说明你知道**只有部分**适合。
- 准备：滚动升级时委托是否会丢、 readiness 要等 WAL 回放完。

## Q8. 消息积压了你怎么排？

**怎么答**：

一套可复用的排查顺序：

1. 是生产突增还是消费变慢（GC、慢 SQL、下游依赖）。
2. 分区是否倾斜（热点币种、热点账户）。
3. 能否水平扩消费者（同一消费组）。
4. 能否丢弃或降级非核心（统计可延迟，成交回报不行）。
5. 积压期间的用户可见性：延迟告警，而不是静默。

对账和绩效都写过 Redis 抗积压，要说明 Redis 是缓冲结果或计数，不是把 Kafka 替代掉。

## Q9. 一次线上事故，你如何用日志 / 指标 / 链路定位？

**怎么答**：

用对账或交易举一个 3 分钟故事：

- Grafana 先看黄金指标：QPS、错误率、消费 lag、DB 连接。
- 再用 trace / 业务单号（委托 ID、充提 ID）进 ELK。
- 最后才 ssh 看实例。
- 复盘输出：告警缺了什么、runbook 补什么。

没有真实事故就用「消费 lag 导致对账窗口超时」这种你系统里必然出现过的场景，不要编戏剧性宕机。

## Q10. 微服务里的分布式事务，成交和账务怎么做？

**怎么答**：

- 热路径避免 2PC。常用：本地事务 + 可靠消息（RocketMQ 事务消息）或 outbox。
- 账务消费幂等，对账系统兜底抓住最终不一致。
- 这正好把交易项目和对账项目连成一条叙事：交易追求快，对账追求对。
