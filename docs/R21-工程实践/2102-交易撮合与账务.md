# 交易撮合与账务

对应简历：数字资产交易平台（公司采购源码，两人搭建）、策略交易系统。面试官默认你碰过**委托 → 撮合 → 成交 → 账务 → 钱包**整条链。先声明引擎来自源码，再证明你读懂并落地过；会从订单簿一路问到资金一致性。

仓库约 70+ Maven 模块，多数是可独立部署的 Dubbo 服务。简历只写业务域和你做过的链路；下面表用来面试对照，不要把目录名堆到简历上。被问「你具体负责哪几个」时，指到交易 / 账本 / 钱包，不说虚数。

## Q1. 价格优先、时间优先具体怎么落地？

**怎么答**：

- 买单按价格从高到低，卖单从低到高；同价按进入撮合引擎的时间。
- 订单簿每个价位是一个队列（FIFO），价位之间用有序结构（简历中的红黑树）导航到最优价。
- 部分成交：剩余量留在同价位队列头部或按规则重新入队，不能丢失时间优先级。
- 市价单：沿对手盘一档档吃，直到量完或触及保护限价。

**追问**：自成交（自己买自己卖）拦不拦、冰山单、被动方手续费，按你真实做过的规则说，没做就明确「规则在撮合前的风控层」。

## Q2. 为什么用红黑树做订单簿，而不是堆、跳表、数组？

**怎么答**：

- 需要：按价格有序、频繁插入撤单、快速取最优价、按价位区间取深度。
- **堆**：取最优 O(1)，但撤单和按价格定位差。
- **有序数组**：深度展示直观，中间插入贵。
- **跳表**：也能有序，实现和调参成本更高。
- **红黑树**：价位有序、插入删除稳定对数；每个节点挂该价位 FIFO 队列。

补充一句：真正热路径是「最优价位队列的头节点成交」，树只负责换档和撤单定位。

## Q3. LMAX Disruptor 在撮合里解决什么问题？

**怎么答**：

- 撮合是单写者或多写者进入、单撮合线程消费的环形队列场景，要尽量无锁、无伪共享。
- Disruptor：预分配环形 buffer、序号协调、避免链表队列的节点分配和锁。
- 典型流水：网关线程投递委托事件 → 撮合线程处理 → 成交 / 深度事件再投递给账务和行情。
- 对比 Kafka：Kafka 是跨进程可靠投递；撮合热路径不能每笔等磁盘复制。Kafka / RocketMQ 放在成交后的异步链路。

**追问**：单线程撮合如何水平扩展？按交易对分片（BTC-USDT 一个引擎），不要说随便加撮合线程抢同一本订单簿。

## Q4. 内存撮合崩溃了怎么办？

**怎么答**：必须有恢复故事，否则内存撮合是扣分项。

常见组合（按你实际用过的说）：

- 委托先写 WAL / 本地磁盘或可靠消息，再进入内存。
- 定时快照订单簿 + 快照后增量事件回放。
- 成交异步落库，恢复时以账务为准还是以撮合日志为准，**必须先定 source of truth**。
- 启动时拒绝新委托，直到回放完成并校验账本平衡。

铜锣是采购源码 + 两人搭建：讲你如何把恢复流程跑通、验证过哪些故障，不要假装设计了整套 WAL。

## Q5. Redis 热数据 + MySQL 异步落库，怎么保证不丢成交？

**怎么答**：

- Redis：盘口、最新成交、用户持仓缓存，服务读多写多。
- MySQL：委托终态、成交、资金流水，对账和监管看这里。
- 风险：进程挂在「已撮合未落库」。要用出站消息表 / RocketMQ 事务消息 / 本地 redo，保证至少一次交给账务。
- 账务要幂等：`成交ID` 唯一，重复回报不能加两次钱。

相关笔记：[Kafka 消息丢失](/docs/R06-消息队列/0600-KFK笔记/060003)、[消息重复](/docs/R06-消息队列/0600-KFK笔记/060004)、[Redis](/docs/R04-Redis笔记/0400)。

## Q6. 合约强平引擎怎么工作？

**怎么答**：

- 标记价（mark price）而不是最新成交价，降低插针对爆仓的影响。
- 扫描：维持保证金率低于阈值进入强平队列，不能每笔成交全量扫所有用户，通常按交易对 + 风险档位索引。
- 执行：吃对手盘或交给强平委托；部分强平 vs 全仓逐仓规则要讲清楚。
- 失败：流动性不足时的接管、自动减仓（ADL）是否存在——没有就说没有，不要编。

简历写了「标记价扫描与强平引擎」，面试官会问扫描周期和热点账户优化。

## Q7. 账户账务如何避免并发把余额打穿？

**怎么答**：

- 同一账户串行：按 `uid` 分区队列 / 账户级锁 / 单线程账本。
- 流水先行：先记不可变 ledger，再更新余额快照。
- 可用 / 冻结 / 保证金分字段，下单冻、成交转、撤单解冻。
- 批处理：流水归档、日终快照、对账补偿，对应简历「账户批处理完成流水归档、余额快照与补偿」。

**追问**：分布式下 Redisson 锁行不行？账务热路径更常见的是分区单线程，锁只用于跨账户或冷操作。见 [分布式锁](/docs/R04-Redis笔记/0403)。

## Q8. Netty WebSocket 推行情，如何扛住万人同订阅？

**怎么答**：

- 公共行情（深度、K 线）做广播组，不要每人一份序列化。
- 私有数据（成交、委托）按用户连接推，鉴权绑定 channel。
- 合并推送、限频、断线补快照 + 增量。
- 和撮合解耦：撮合线程绝不直接写网络，只丢事件。

## Q9. 70+ 模块按什么拆？会不会拆过头？

**怎么答**：

- 按领域拆，对照上面的服务域表：账户、委托、撮合、行情、钱包、用户、OTC。这是源码的拆法，不是你现场拆的。
- 拆的收益：独立扩容（撮合和运营后台负载完全不同）、失败隔离。
- 代价：分布式事务、联调、配置（Apollo）、治理（Dubbo + ZK）。
- 资深表达：核心交易链路保持少跳数；后台和统计可以拆得更碎。ES 做对账检索，不要让撮合查 ES。
- 两人搭建时要能讲：哪些服务是启动交易的最小集，哪些可以后启。

## Q10. 策略交易机器人和撮合引擎有什么本质区别？

**怎么答**：

- 策略机器人是**交易所的客户**：调 REST/WS 下单，优化的是延迟、撤单、风控熔断。
- 撮合引擎是**交易所的核心**：维护公平性和一致性。
- 简历里两者都有，介绍时先声明身份，避免把「我写过套利机器人」说成「我写过币安撮合」。
