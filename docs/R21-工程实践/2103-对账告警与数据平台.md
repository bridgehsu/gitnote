# 对账告警与数据平台

对应简历：对账告警明星项目、数据平台整合、数仓 V3、绩效激励 / 用户画像。这是最容易用数字打穿的一块，也是最能证明你「资深」的一块。

## Q1. 对账到底对什么？三条资金流怎么对？

**怎么答**：

简历覆盖钱包、交易所、支付：

- **钱包**：链上充提 vs 平台钱包账本 vs 用户余额。
- **交易所**：成交账务 vs 委托冻结 vs 手续费 / 返佣。
- **支付**：三方支付单 vs 内部充值单 vs 到账余额。

对账不是一张大表 join。常见分层：

1. 日终总额（币种级）。
2. 账户级差异。
3. 流水级定位。

「5,000+ 资产数据」要说清是 5,000+ 币种/账户快照还是 5,000+ 流水，面试官只接受一种口径。

## Q2. 为什么定位能从 24 小时以上缩到 1–2 小时？

**怎么答**：拆成「发现 + 定位」，不要只说上了 Kafka。

- 以前：T+1 导出、Excel、跨部门对口。
- 现在：上游指标近实时进 Kafka → 落库 → 按币种规则算差异 → 异步告警 → 运营看报表和审批。
- 1–2 小时：从告警产生到能指出差异账户 / 差异类型（充提未入账、手续费漏记、分片漏数）。
- 不是 1–2 小时完成调账。调账往往还要财务审批。

## Q3. 99.9% 准确率怎么定义？漏账怎么办？

**怎么答**：

- 准确率：对平记录 / 应对比记录。要排除「规则关闭的币种」「尚未终态的充提」。
- 漏报比误报更危险：资金缺口没发现。用总额兜底（平台负债 vs 链上资产）抓系统性漏账。
- 误报：确认数不够、时钟、时区、精度（小数位）、内部划转未排除。规则可配置（Apollo）才能快速降噪。
- 死信与重试：告警指数退避，避免把下游打爆，同时不能把失败吞掉。对应简历「告警指数退避重试 + 死信队列」。

## Q4. Kafka 对接上游后，对账计算为什么还要 Redis 和 ShardingJDBC？

**怎么答**：

- Kafka：解耦上游、削峰、可回放。
- Redis：热点规则、币种配置、最近差异缓存，降低每次打 DB。
- ShardingJDBC：资产指标表按币种或日期水平分片，日增量很大。
- ES：异常明细检索给运营，不是计算引擎。

计算本身可以在消费端本地完成，DB 存结果。不要说「用 ES 做对账计算」。

相关：[Kafka 消费组](/docs/R06-消息队列/0600-KFK笔记/060006)、[分区](/docs/R04-Redis笔记/0402)。

## Q5. 对账任务失败了如何保证不漏、不重？

**怎么答**：

- 消费至少一次 + 结果表唯一键（批次号 + 账户 + 币种 + 对账窗口）。
- 窗口按块时间 / 业务日切，不要用「现在」这种滑动口径做资金对账。
- 回放：从 Kafka offset 或按窗口重跑；重跑必须覆盖写。
- 与 [消息重复](/docs/R06-消息队列/0600-KFK笔记/060004) 同一套幂等思维。

## Q6. 数据平台「统一计算中心和下载中心」解决什么？

**怎么答**：

- 痛点：各业务自己算指标、自己导数据，口径不一致，重复造任务。
- 计算中心：指标定义、调度、权限、产出表。
- 下载中心：脱敏、限流、审计、大文件异步。
- 你补的基础服务：网关、登录、系统管理，让数据能力变成产品而不是脚本。

这对应「数据能力产品化，支持业务自助配置」。面试官会问：业务方如何配一个新指标而不改代码？准备「配置系统 + 审批 + 版本」答案。

## Q7. 数仓 V3 建设周期 6 个月变 3 个月，你做了哪一层？

**怎么答**：

- 不要说「我把 Hive 调快了一倍」。
- 简历点是**数据接入服务设计**：标准化接入、减少每个数据源从零对接。
- 50% 效率：新数据域接入人天下降，从而整体工期减半。
- 准备一个例子：以前接一个上游要改 5 个仓库作业，现在只登记 schema / 主题 / 权限。

## Q8. Spark 离线和 Flink 实时在绩效系统里怎么分工？

**怎么答**：

- **离线 Spark**：T+1 稳定指标、对账型汇总、方案全量核算。
- **Flink 实时**：当天进度、预估奖金、看板，允许轻微误差。
- 绩效发放以离线为准，实时只作过程可见。
- RocketMQ 解耦上游事件；Redis 抗消费积压；Redisson 锁防同一核算对象并发结算。

「覆盖 2,000+ 商超」强调的是核算对象规模和分片，不是 2,000 个并发连接。

---

## Q9. 离线指标试算如何做到节约约 30% 计算成本？

**怎么答**：

- 全量核算贵在：大表 shuffle、重复扫 Hive、无效方案也跑完整作业。
- 试算：用已有离线指标结果 + 抽样门店 / 抽样员工跑公式，先暴露配置错误。
- 30%：减少返工全量作业的次数（准备：试算拦截了多少次错误方案）。
- 风险：抽样偏差。要说明哪些方案仍必须全量（涉及封顶、跨门店分摊）。

## Q10. 用户画像 / DMP 和绩效指标是不是同一套数仓？

**怎么答**：

- 可以共用采集和 ID 映射，但服务目标不同：画像是标签和圈人，绩效是可审计的金额。
- 绩效指标要可解释、可追溯到人 / 天 / 门店；画像可以近似。
- 面试里主动提「发钱的链路必须可审计」，能体现金融 / 零售场景意识。

---

## Q11. Prometheus / Grafana / ELK 在对账系统里各看什么？

**怎么答**：

- Prometheus：消费延迟、窗口成功率、规则耗时、告警发送失败率。
- Grafana：值班看板，SLO（例如窗口完成 99%、告警延迟 < 5min）。
- ELK：差异明细和错误栈，给人和财务查，不替代指标系统。

资深表达：没有 SLO 的监控只是「有图」。
